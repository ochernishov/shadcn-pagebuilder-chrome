# SeniorDev: Манифест и Закон Разработки Проектов

**Проект:** `shadcn-pagebuilder-chrome`

**Статус документа:** Обязателен к исполнению для всех разработчиков и ИИ-агентов.
**Цель:** Обеспечить предсказуемость, масштабируемость, безопасность и отчуждаемость
кодовой базы на всех этапах жизненного цикла проекта. Ниже описаны фундаментальные
законы проектирования, нарушения которых недопустимы.

> **Как этот файл меняется.** Текст закона одинаков во всех проектах COS. Проект
> отклоняется от него **только там, где стек или архитектура физически требуют
> иного**, и каждое отклонение записывается в раздел «Отклонения в этом проекте»
> внизу файла — с причиной и ссылкой на ADR. Отклонение без записи считается
> нарушением, а не особенностью проекта.

## 1. Архитектура и Проектирование (Макро и Микро)

### 1.1. Domain-Driven Design (Макро-уровень)
*   **Ограниченные контексты:** Проект разделяется на изолированные бизнес-домены (например, `CRM`, `HR`, `Billing`).
*   **Единый язык:** Код (названия классов, папок, переменных) должен говорить на языке бизнеса.
*   **Слоистая архитектура:** Внутри каждого домена соблюдается луковая архитектура (Domain -> Application -> Infrastructure). Бизнес-логика ничего не знает о базах данных или фреймворках.
*   **Правило Spin-off:** Если микросервис получает свою уникальную аудиторию (внешнюю вместо внутренней) или высокий коммерческий потенциал, он выносится в Standalone-приложение с интеграцией через API и SSO.

### 1.2. Глубокие модули (Микро-уровень)
*   **Интерфейс:** Должен быть минимальным и простым для вызывающего кода.
*   **Реализация:** Должна скрывать внутри себя максимальную сложность.
*   **Швы (Seams) и Адаптеры:** Зависимости не создаются внутри модулей, а передаются извне. Модуль должен быть спроектирован так, чтобы любую инфраструктурную часть (базу, платежный шлюз) можно было подменить фейковым адаптером для тестов.

## 2. Инфраструктура и Развертывание (IaC и CI/CD)

### 2.1. Инфраструктура как код (DevOps & IaC)
*   **Серверы — это стадо, а не питомцы:** Запрещена ручная конфигурация серверов по SSH.
*   **Контейнеризация:** Все приложения оборачиваются в `Dockerfile`. Связи между сервисами описываются исключительно в `docker-compose.yml`.
*   **Disaster Recovery:** Инфраструктура должна быть готова к полному развертыванию на пустом сервере за 15 минут из репозитория и бэкапа базы данных.

### 2.2. Непрерывная интеграция (CI/CD)
*   **Запрет деплоя с локальных машин:** Запрещено использовать `pm2` или скрипты для прямой загрузки кода на Production.
*   **Единый источник правды:** Релиз происходит строго через GitHub Actions. Сервер CI/CD выполняет Lint-проверки, прогоняет тесты и собирает проект.
*   **Изоляция сред:** Миграции и новый код сначала развертываются на Staging-сервере, и только после успешных проверок — на Production.

### 2.3. Git Flow
*   **Правило одной задачи:** Одна задача = одна ветка (`feature-branch`).
*   **Запрет работы в Main:** Ветка `main` содержит только 100% рабочий код.
*   **Синхронизация:** Постоянное подтягивание изменений из `main` в рабочую ветку для предотвращения масштабных merge conflicts.

## 3. Безопасность и Работа с Данными

### 3.1. Базы данных и Row Level Security
*   **Row Level Security:** Каждая новая таблица в базе данных должна создаваться с включенным RLS. Публичный доступ к таблицам строго запрещен.
*   **Политики доступа:** Доступ к данным реализуется на уровне PostgreSQL через Policies (с использованием `auth.uid()`), а не через фильтры на фронтенде.
*   **Безопасные миграции:** ИИ-агенты и разработчики тестируют миграции БД локально, отправляют скрипты в репозиторий, после чего CI/CD применяет их к боевой базе.

### 3.2. Обмен данными (Микросервисы)
*   **Асинхронность:** Сервисы внутри экосистемы общаются преимущественно асинхронно через Брокеры сообщений (RabbitMQ / логи БД), а не через прямые HTTP-вызовы, чтобы избежать каскадных падений.

---

## 4. Фронтенд-Архитектура (Next.js)

### 4.1. Парадигма Server-First
*   По умолчанию все компоненты являются **Server Components**. Они выполняют запросы к БД и отдают чистый HTML.
*   Запрещено использование директивы `'use client'` на уровне корневых файлов и Layout.

### 4.2. Островки интерактивности
*   Клиентский JavaScript (`'use client'`, хуки `useState`, `useEffect`) изолируется в минимально возможных дочерних компонентах (кнопки, формы, модальные окна).

### 4.3. Мутации
*   Изменение данных на сервере производится через **Server Actions**, заменяя избыточные API-роуты и тяжелые клиентские библиотеки управления состоянием.

## 5. Архитектурная Память (Документация)

### 5.1. Журнал решений (ADR)
*   Любое значимое изменение в архитектуре (выбор стека, разделение доменов, паттерны безопасности) фиксируется в папке `docs-<project>/adr/`.
*   **Формат файла:** Название, Статус, Контекст (почему возникла проблема), Решение, Последствия (плюсы и минусы).
*   **Правило контекста:** Перед началом работы над любой задачей, ИИ-агент или новый разработчик обязан ознакомиться с содержимым директории `adr/`, чтобы действовать в рамках принятых договоренностей.

> Путь `docs-<project>/adr/`, а не `docs/adr/` — в COS папка документации несёт имя
> репозитория (в Obsidian подключён единый vault на всю `React/`, и просто `docs/`
> неразличима между проектами). Канон размещения, нумерация и шаблон — скилл
> `documentation`; расширенный шаблон для решений о границах доменов — `domain-design`.
